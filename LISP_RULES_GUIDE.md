# Як читати і писати s-expr-правила (LISP + Clojure)

Людський підручник до s-expr-нотації правил і задач: LISP-ядро, Clojure-шар і спільний
синтаксис — від базових атомів до повних постановок, приклади в кінці. Нормативна
специфікація для агентів — `DOC_STANDARD.md` → Rule Style.

Канонічний глосарій нотації — ОДИН, у `~/.claude/CLAUDE.md` → «LISP/Clojure-like task
notation»: самодостатня таблиця (форма + читання + приклад), яку автоматично бачить
кожен агент і сабагент у КОЖНОМУ проєкті. Контракт живе ТІЛЬКИ там; цей гайд — особистий
підручник користувача, жоден агентський док на нього не посилається. Новий оператор чи
літерал: рядок у каноні — обов'язково, розгорнутий розділ тут — для себе.

## 1. Про нотацію

Задача чи правило ставиться у ТРЬОХ рівноправних формах: проза, чистий LISP s-expr,
Clojure-форми (threading, літерали). Це нотація, не програма: ніщо не обчислюється,
критерій правильності — прочитати рядок уголос.

Від Lisp запозичена лише **s-expression-нотація**: дужки, суб'єкт першим елементом,
`;;` коментар, `:keyword`-кваліфікатори (відлуння keyword-аргументів Common Lisp).
Свідомі розбіжності з канонічним Lisp:

- Канонічний Lisp — **мова, що виконується**: перший елемент списку — функція, решта —
  її аргументи, все обчислюється. Наші рядки ніхто не виконує — це нотація для правил.
- `→`, `|`, CAPS-наголос — власні оператори цієї нотації; у Lisp їх нема.
- Немає семантики обчислення, quoting, макросів — і не треба.

Тобто це **DSL у s-expr-одязі**: від Lisp взято рівно те, що робить запис однозначним і
сканованим (структура дужок), а не мову цілком. Перевіряти запис Lisp-інтерпретатором
безглуздо. Хто що вніс у словник — §13.

## 2. Атоми і дужки — будівельні блоки

Спільний фундамент обох мов — з чого складається будь-який рядок:

| Блок                 | Походження | Що це                                          | Приклад                                    |
| -------------------- | ---------- | ---------------------------------------------- | ------------------------------------------ |
| слово в kebab-case   | наше       | суб'єкт/концепт                                | `startup-bulk-work`                        |
| точне ім'я API       | наше       | літеральний якір — трактується буквально       | `EventCleanupSystem`, `DistrictBuildUIView` |
| CAPS                 | наше       | наголос на критичному слові                    | `NEVER`, `ONLY`, `FAIL LOUD`, `NEW`        |
| `;;`                 | LISP       | коментар — зазвичай «чому»                     | `;; cleanup знищив би його`                |
| `:keyword`           | Clojure    | самозначуща мітка: не змінна, не рядок — маркер | `:only`, `:session`, `:must-not`           |
| `( )`                | LISP       | правило / дія / механіка — одиниця сенсу       | `(subject → verdict)`                      |
| `[a b c]`            | Clojure    | вектор: упорядкований список, БЕЗ ком          | `[BuildDistrictAction/ DistrictBuildUIView]` |
| `{:k v, :k2 v2}`     | Clojure    | мапа дрібних полів; кома = пробіл, можна не писати | `{:skip тести  :result фікс}`          |

Clojure-літерали в оригіналі — щоб бачити, звідки вкрадено:

```clojure
{:name "Lviv" :tier 2}      ;; мапа: ключі — keywords
(:tier city)                ;; «дістань поле :tier з city»
["BuildDistrictAction" "DistrictBuildUIView"]   ;; вектор рядків
```

Правило вибору дужок: круглі — коли щось СТВЕРДЖУЄТЬСЯ (є суб'єкт і вердикт);
квадратні — коли просто перелік; фігурні — коли кілька пар ключ→значення, надто
дрібних для власних дужок.

## 3. Анатомія рядка

```text
(subject :qualifier → verdict)   ;; why
 └──┬──┘ └───┬────┘   └──┬──┘       └┬┘
 про що    за якої     що робити /   чому це правило
           умови       що має бути   взагалі існує
```

**Порядок читання** — не зліва направо, а у три кроки:
1. `subject → verdict` — кістяк: «X іде туди / X має бути таким».
2. `:qualifier` — звузити: «...але тільки у варіанті Y».
3. `;; why` — довіритись або перевірити: «бо Z».

Приклад: `(place :di :feature → "<Feature>/Installer/")` читається як
**«DI-код фічі кладемо у Installer/ цієї фічі»** — subject `place`, два кваліфікатори
звужують до "DI, рівень фічі", вердикт — шлях.

## 4. Потік — одна думка, два записи

**Ланцюжок стрілок** `A → B → C` — конвеєр: кожна стрілка читається окремо — «A породжує B,
B породжує C». У вердикті це послідовність/наслідок (`listens event → creates entity`); у
лапках заголовка задачі (§11) — взагалі не оператор, а вільний текст: схема потоку словами.
Структурний сенс має лише ОДНА стрілка на рівні дужки — та, що відділяє
суб'єкт+кваліфікатори від вердикту. ASCII `->` еквівалентний `→`.

**Threading `(-> A B C)`** (Clojure) — той самий конвеєр, записаний формою. У Clojure
`(-> x f g)` виконувано «протягує» x крізь f у g — спосіб записати конвеєр зліва направо
замість вкладених дужок, що читаються зсередини назовні:

```clojure
(-> city (assoc :tier 3) (update :population inc))
;; те саме без ->, навиворіт: (update (assoc city :tier 3) :population inc)
```

У нас threading — канонізований рівноправний запис потоку (рядок у глобальній таблиці):

```lisp
(-> confirm-click DistrictBuildRequestEvent BuildOrchestratorSystem district-entity)
;; ≡ confirm-click → DistrictBuildRequestEvent → BuildOrchestratorSystem → district-entity
```

Коли який запис: **стрілки** — коли в ланках є вердикти чи кваліфікатори (кожна ланка —
повноцінне правило); **threading** — коли це чистий конвеєр імен без побічних полів,
особливо всередині `goal`. Агент читає обидва однаково.

## 5. Словник операторів

| Форма                | Як читати                       | Приклад                                                       |
| -------------------- | ------------------------------- | ------------------------------------------------------------- |
| `→`                  | «іде в / стає / роби так»       | `(runtime-logic :default → reactive-system)`                  |
| `(-> A B C)`         | «конвеєр: A крізь B у C» — те саме, що ланцюжок `A → B → C` (§4) | `(-> click event orchestrator)`              |
| `\|`                 | «або» (рівноцінні альтернативи) | `(startup-bulk-work → pipeline-stage \| sub-system)`          |
| `:requires X`        | «зобов'язане мати X»            | `(table-key :requires IEquatable<T> + GetHashCode)`           |
| `:only-when X`       | «дозволено лише коли X»         | `(installer :mono → only when it owns [SerializeField] data)` |
| `:never X` / `NEVER` | «ніколи; заборонено»            | `(key-as-discriminator → NEVER)`                              |
| `:must-not X`        | «не сміє робити X»              | `(loader :must-not → per-frame or gameplay logic)`            |
| `:contains X`        | «складається лише з X»          | `(orchestrator :contains no-domain-logic)`                    |
| `:in <місце>`        | «живе у <місці>»                | `(naming → "…Event" :in Events/)`                             |
| `:exists-only-under X` | «існує лише під X»            | `(sub-system :exists-only-under orchestrator)`                |
| `?` (вердикт)        | «поле навмисно відкрите — СПИТАЙ, не вигадуй» | `(scope :only → ?)`                             |
| CAPS                 | наголос на критичному слові     | `FAIL LOUD`, `ONLY`, `RETAIN`                                 |

**Стаковані кваліфікатори** — кілька `:qualifier` поспіль читаються через «І», кожен звужує
попереднє: `(grep-family :session main :grep-budget<4 → ALLOW)` = «grep-подібний пошук, у
головній сесії, І поки бюджет < 4 — дозволено». Це завжди звуження, не альтернативи;
порядок — від ширшого до вужчого.

## 6. Три типи правил — вибирай форму за питанням

```text
Питання, на яке відповідає правило        →  Форма
«куди це покласти / що з цим зробити?»    →  дія:        (subject → verdict)
«що про це завжди істинно?»               →  інваріант:  (subject :requires/:never/:contains …)
«а якщо по-різному?»                       →  розгалуження: §6.1
```

### 6.1 Розгалуження — дві форми, спільне читання

Розгалуження ніколи не ховається в «якщо-то» всередині тексту — це завжди **набір
гілок**, кожна читається як `умова → результат`. Форму задає те, ЩО розгалужується.

**Дизайн-варіанти** — «який режим цієї речі?». Взаємовиключні різновиди, які ти
*авторуєш*; порядок не пріоритет. Пиши **по рядку на варіант**, суб'єкт спільний,
різницю несе `:qualifier`:

```lisp
(box :flatten → release in finally)
(box :wrap    → RETAIN in a field, release in OnDispose)
```

Читається: «box у режимі flatten → …; box у режимі wrap → …». `:qualifier` каже, ЯКИЙ це варіант.

**Рантайм-умова** — «якщо стан такий → дія така». Гілки перевіряються на льоту,
**порядок = пріоритет**. Пиши `cond` (канон): тести згори вниз, перший істинний виграє:

```clojure
(cond
  (< gold cost)        :not-enough-gold
  (district-occupied?) :tile-busy
  :else                (build-district!))
```

Читається: «якщо gold < cost → вердикт `:not-enough-gold`; інакше якщо тайл зайнятий →
`:tile-busy`; інакше → виконати `build-district!`». `:else` — дефолт для тотальності;
`!` у `build-district!` (Clojure-конвенція) маркує гілку, що МУТУЄ світ, — решта чисті вердикти.

**Спільне в обох формах:** гілка = `умова → результат`, і лишається читаною вголос.
Різниця — вісь: `:qualifier` розрізняє *авторовані різновиди* (порядок байдужий), `cond` —
*рантайм-стани* (перший збіг виграє). Результат гілки — одне з трьох:

| Результат гілки           | Коли                                | Приклад |
| ------------------------- | ----------------------------------- | ------- |
| `:keyword`-вердикт         | гілка лише *називає* висновок        | `:not-enough-gold` |
| мапа `{:verdict … :do …}`  | вердикт + реакція на нього           | `{:verdict :tile-busy :do "show popup"}` |
| дія-форма `(do!)`          | гілка *виконує* роботу (мутує світ)  | `(build-district!)` |

Мапу-результат тримай **парною** — Clojure-літерал вимагає пар ключ→значення
(`{:tile-busy :do "popup"}` — три форми, НЕвалідно). Які саме записи мапи ми ще
зважуємо — §12.0.

## 7. Інваріанти — детально

Інваріант описує **властивість, що тримається завжди**, а не крок, який треба виконати.
Пізнається за тим, що вердикт — не місце і не дія, а обмеження:

```lisp
(per-frame-system   :requires written-justification)   ;; нема письмового «чому не reactive» = смердить декомпозицією
(sub-system         :exists-only-under orchestrator)
(world-component    :not-query-matchable)               ;; With<T>/WhenAdded<T> його НЕ бачать
(persistent-data-entity :never-carries EventTag)        ;; cleanup знищив би його
```

Як читати: підстав слово «завжди» — «per-frame система **завжди** вимагає письмового
обґрунтування», «сутність із персистентними даними **ніколи** не носить EventTag».

Як писати новий інваріант:
1. Сформулюй прозою через «ніколи» або «завжди»: *«ключ таблиці ніколи не буває без IEquatable»*.
2. Суб'єкт — те, до чого прикладається обмеження: `table-key`.
3. «завжди має» → `:requires`; «ніколи не» → `:never…` / `:must-not`; «складається лише з» → `:contains`.
4. У `;; why` — наслідок порушення: що зламається. Це найкорисніша частина інваріанта.

Типова помилка — сховати ДІЮ в інваріант: `(loader :requires validate-then-MarkAsLoaded)` —
це не властивість, це порядок кроків. Пиши як дію: `(order → validate, THEN MarkAsLoaded())`.

## 8. Вкладення

Вкладення — це **анкета одного суб'єкта**: зовнішня дужка задає контекст, внутрішні — його
поля. Використовуй, коли в одного суб'єкта 3+ аспекти, які втрачають сенс окремо:

```lisp
(routing :spawn
  (loop            → per config entry, TrySpawn down the list, first match wins)
  (input           → one authored config → one owner)
  (unhandled-kind  → FAIL LOUD)                ;; кайнд без спавн-підсистеми = баг авторингу
  (use-for         → materializing config → entities))
```

Як читати: зовнішній рядок — заголовок («режим routing, варіант spawn»), внутрішні — його
характеристики. Поля всередині НЕ читаються без контексту зовнішньої дужки.

Правила вкладення:
- **Глибина ≤ 2.** Третій рівень означає, що ти описуєш структуру даних, а не правило —
  розбий на два суб'єкти.
- **Вкладати можна тільки залежне.** Якщо внутрішній рядок має сенс сам по собі — це
  окреме правило верхнього рівня, не поле анкети.
- **Паралельні анкети — поруч і з однаковими полями** (як `routing :spawn` та
  `non-routing :evaluator` у PATTERN_POLYMORPHIC_CATALOGUE) — тоді різниця читається як діф.

## 9. Групування і вирівнювання

- Секції всередині одного fence — коментар-розділювач: `;; ── назва секції ─────────`.
- Колонка `→` вирівнюється пробілами: сканування таблиці очима — половина її цінності.
- Один рядок = одне правило. Два правила через кому в одному рядку — не пиши.

## 10. Як писати

### Алгоритм (шпаргалка)

1. Скажи правило вголос одним реченням.
2. Знайди суб'єкт (про що воно?) — він іде першим, у kebab-case або як точне ім'я API.
3. Вибери тип за §6: дія / інваріант / розгалуження.
4. Вербалізуй вердикт коротко; альтернативи — через `|`; критичне слово — CAPS.
5. Додай `;; why` одним підрядним. Не влазить в одне підрядне? Це design decision —
  пиши прозовий абзац, а не рядок таблиці.
6. Перечитай уголос за схемою §3. Якщо речення не складається — правило сформульоване криво.

### Що НЕ конвертувати в таблиці

Проза лишається прозою для: **інтенту** (навіщо модуль існує), **rationale** (чому так
спроєктовано), **поведінкових контрактів** (side-effects, live-vs-copy, порядок викликів).
Нюанс там і є корисним навантаженням — таблиця його вб'є. Евристика: якщо для правила
хочеться другого речення — це не правило.

## 11. Постановка задачі

Користувач ставить задачу компактним s-expr замість прози, коли **логічний зв'язок легше
показати стрілками, ніж описати словами**. Це НЕ Engineering Task Template у дужках —
у LISP їде тільки суть (`goal`); решту блоків шаблону агент добирає питаннями, як завжди.

Форма — анкета §8 із суб'єктом `task`:

```lisp
(task "заголовок: A → B → C"                      ;; ланцюжок потоку, не назва тікета
  (goal
    (mechanic-a → NEW що-створити, коли/де спрацьовує)
    (mechanic-b → NEW система; listens X → creates Y))
  ;; опційні поля — кожне присутнє знімає відповідне питання агента:
  (scope :only  → [файл/ папка/ …])
  (off-limits   → [що поза scope])
  (pattern      → Patterns/PATTERN_*.md)
  (decided      → що вже вирішено)
  {:skip що-не-робити  :result очікуваний-вихід})
```

Як читати:
- **Заголовок** — ланцюжок «що звідки куди тече», не назва тікета.
- **`goal` — по одній внутрішній дужці на механіку** (глибина 2 — стеля, §8). Кожна дужка —
  одна річ, яку можна обговорити/прийняти/відхилити окремо.
- **`NEW`** (CAPS, §2) позначає те, що треба СТВОРИТИ — на відміну від існуючих імен,
  які є контекстом.
- Стрілка всередині дужки — потік (§4): `listens event → creates entity` читається як
  «споживає X і внаслідок цього продукує Y»; чистий конвеєр імен можна записати
  threading-формою `(-> A B C)`.
- **Опційні поля після `goal`** — кожне присутнє знімає питання відповідного блоку шаблону:
  `scope :only` = «Працюй тільки в», `off-limits` = «Не дивись», `pattern` = «Роби за
  шаблоном», `decided` = «Архітектурні рішення», мапа `{:skip … :result …}` = «Не потрібно»
  + «Результат».

Контракт для агента:
- Такий s-expr = блок «Задача» шаблону, точніший за прозовий. Гейт шаблону діє як завжди:
  блоки, яких у постановці нема (scope, pattern, рішення, skip, результат), агент
  **питає, не вигадує** — але тепер питання цілиться у конкретну дужку `goal`.
- Точні імена у дужках (типи, view, папки) — якорі: агент трактує їх буквально,
  а не як приблизний опис.
- За бажанням користувач МОЖЕ додати поля-анкети поруч із `goal` (`scope :only`, `off-limits`,
  `pattern`, `decided`, `{:skip … :result …}` — повний скелет: CLAUDE.md → Engineering Task
  Template) — тоді відповідне питання знімається. Відсутнє поле ≠ «нема обмежень»,
  відсутнє поле = «спитай».

Як набрати `→` на маку — системної комбінації для цього символа нема, тож:
- **Text Replacement** (найзручніше): System Settings → Keyboard → Text Replacements,
  додай заміну `->` → `→` — далі стрілка друкується сама у будь-якому аппі;
- разово: `Ctrl+Cmd+Space` (Character Viewer) → пошук *rightwards arrow*;
- **або просто пиши ASCII `->`** — у постановці задачі він еквівалентний `→`,
  агент читає обидва однаково.

## 12. Приклади

### 12.0 ЧЕРНЕТКА / на твій розгляд

> ⚠️ **Форми, що ми пробували в діалозі, але ще НЕ канон.** Дивись сюди першим — тут рішення
> за тобою, який запис стає домашнім стилем.
>
> **1. Яка мапа-результат гілки `cond`.** Коли гілка несе вердикт + реакцію, пробували три
> парні записи (обрати один як канон):
> - **A — вердикт явним полем** (масштабується, легко докласти `:severity`/`:retry?`):
>   `{:verdict :not-enough-gold :do "show log"}`
> - **B — вердикт-ключ → мапа-реакція** (вердикт «головний», але подвійна вкладеність):
>   `{:not-enough-gold {:do "show log"}}`
> - **C — вердикт-ключ → дія напряму** (найкоротше, якщо лейбл `:do` зайвий):
>   `{:not-enough-gold "show log"}`
>
> **2. `:do` як deliverable-різак.** У постановці задачі `:do` вживали не лише як «що зробити»,
> а як **звужувач scope результату**: `:do {:what "base subsystem type" :type "UniTask based"}` =
> «створи РІВНО цей артефакт, такого роду» — знімає питання «а що ще?». Кандидат у §11 як окреме
> поле-анкети поряд із `:result`.
>
> **3. Застереження «один ключ = одна вісь».** Той самий `:type` на двох рівнях
> (`… :type "Reactive orchestrator" … :do {… :type "UniTask based"}`) читається як каламбур:
> зовні — рід оркестратора, всередині — модель виконання. Вкладеність їх формально розрізняє,
> але надійніше не переобтяжувати ключ: `:do {:what … :exec "UniTask based"}`.

## 13. Походження і полиця

**LISP дав** s-expr-структуру: дужки, суб'єкт першим елементом, `;;` коментар,
keyword-аргументи як прообраз кваліфікаторів.

**Clojure дав** літерали і форми. Clojure (Річ Гікі, 2007) — сучасний Lisp на JVM:
функційний, незмінні дані за замовчуванням. Для цього гайду він цікавий не як мова,
а як **донор нотації**: його s-expr розширений літералами, яких у класичному Lisp нема —
`:keyword` як самозначуща мітка, вектор `[a b c]`, мапа `{:k v}`, threading `(-> x f g)`.
Найцікавіший збіг: наш заголовок задачі `"confirm click → event → orchestrator"` — рівно
думка threading-макроса, знайдена незалежно; тепер обидві форми канонізовані як
рівноправні (§4).

**Канонізовано зараз:** `:keyword`, `[a b c]`, `{:k v}`, `(-> A B C)` threading,
`(cond … :else …)` розгалуження — кожне має рядок у глобальній таблиці.

**На полиці — крадемо, коли знадобиться:**
- `#{a b c}` — множина: елементи без порядку і без дублів (на відміну від вектора);
- `^:meta` — теги на дужках: `^:optional (mechanic → …)` «nice to have»,
  `^:risky` «обговорити перед стартом»;
- `:economy/ap` — namespaced keyword: якір з простором імен, «ap у домені Economy».

Правило для експериментів з формою: дозволено все, що агент прочитає однозначно вголос;
контрактом новий літерал стає через рядок у канонічній таблиці (`~/.claude/CLAUDE.md`) —
без рядка там він лишається здогадкою агента, хоч би як детально був описаний тут.
