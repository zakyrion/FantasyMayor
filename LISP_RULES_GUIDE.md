# Як читати і писати LISP-правила

Людський підручник до s-expr стилю правил у цьому репозиторії. Нормативна специфікація для
агентів — `DOC_STANDARD.md` → Rule Style; цей файл — тренажер для людини: як читати вголос,
як писати самому, і окремо — інваріанти та вкладення.

## 1. Анатомія рядка

```text
(subject :qualifier → verdict)   ;; why
 └──┬──┘ └───┬────┘   └──┬──┘       └┬┘
 про що    за якої     що робити /   чому це правило
           умови       що має бути   взагалі існує
```

**Порядок читання** — не зліва направо, а у три кроки:
1. `subject → verdict` — кістяк: «X іде туди / X має бути таким».
2. `:qualifier` — звузити: «...але тільки у варіанті Y».
3. `;; why` — довіритись або перевірити: «бо Z».

Приклад: `(place :di :feature → "<Feature>/Installer/")` читається як
**«DI-код фічі кладемо у Installer/ цієї фічі»** — subject `place`, два кваліфікатори
звужують до "DI, рівень фічі", вердикт — шлях.

## 2. Словник операторів

| Форма                | Як читати                       | Приклад                                                       |
| -------------------- | ------------------------------- | ------------------------------------------------------------- |
| `→`                  | «іде в / стає / роби так»       | `(runtime-logic :default → reactive-system)`                  |
| `\|`                 | «або» (рівноцінні альтернативи) | `(startup-bulk-work → pipeline-stage \| sub-system)`          |
| `:requires X`        | «зобов'язане мати X»            | `(table-key :requires IEquatable<T> + GetHashCode)`           |
| `:only-when X`       | «дозволено лише коли X»         | `(installer :mono → only when it owns [SerializeField] data)` |
| `:never X` / `NEVER` | «ніколи; заборонено»            | `(key-as-discriminator → NEVER)`                              |
| `:must-not X`        | «не сміє робити X»              | `(loader :must-not → per-frame or gameplay logic)`            |
| `:contains X`        | «складається лише з X»          | `(orchestrator :contains no-domain-logic)`                    |
| `:in <місце>`        | «живе у <місці>»                | `(naming → "…Event" :in Events/)`                             |
| CAPS                 | наголос на критичному слові     | `FAIL LOUD`, `ONLY`, `RETAIN`                                 |

**Ланцюжок стрілок** `A → B → C` — конвеєр: кожна стрілка читається окремо — «A породжує B,
B породжує C». У вердикті це послідовність/наслідок (`listens event → creates entity`); у
лапках заголовка задачі (§10) — взагалі не оператор, а вільний текст: схема потоку словами.
Структурний сенс має лише ОДНА стрілка на рівні дужки — та, що відділяє
суб'єкт+кваліфікатори від вердикту.

**Стаковані кваліфікатори** — кілька `:qualifier` поспіль читаються через «І», кожен звужує
попереднє: `(grep-family :session main :grep-budget<4 → ALLOW)` = «grep-подібний пошук, у
головній сесії, І поки бюджет < 4 — дозволено». Це завжди звуження, не альтернативи;
порядок — від ширшого до вужчого.

## 3. Три типи правил — вибирай форму за питанням

```text
Питання, на яке відповідає правило        →  Форма
«куди це покласти / що з цим зробити?»    →  дія:        (subject → verdict)
«що про це завжди істинно?»               →  інваріант:  (subject :requires/:never/:contains …)
«а якщо варіант інший?»                   →  розгалуження: два рядки з різними :qualifier
```

Розгалуження — це ДВА рядки, не один з «якщо-то» в тексті:

```lisp
(box :flatten → release in finally)
(box :wrap    → RETAIN in a field, release in OnDispose)
```

## 4. Інваріанти — детально

Інваріант описує **властивість, що тримається завжди**, а не крок, який треба виконати.
Пізнається за тим, що вердикт — не місце і не дія, а обмеження:

```lisp
(per-frame-system   :requires written-justification)   ;; нема письмового «чому не reactive» = смердить декомпозицією
(sub-system         :exists-only-under orchestrator)
(world-component    :not-query-matchable)               ;; With<T>/WhenAdded<T> його НЕ бачать
(persistent-data-entity :never-carries EventTag)        ;; cleanup знищив би його
```

Як читати: підстав слово «завжди» — «per-frame система **завжди** вимагає письмового
обґрунтування», «сутність із персистентними даними **ніколи** не носить EventTag».

Як писати новий інваріант:
1. Сформулюй прозою через «ніколи» або «завжди»: *«ключ таблиці ніколи не буває без IEquatable»*.
2. Суб'єкт — те, до чого прикладається обмеження: `table-key`.
3. «завжди має» → `:requires`; «ніколи не» → `:never…` / `:must-not`; «складається лише з» → `:contains`.
4. У `;; why` — наслідок порушення: що зламається. Це найкорисніша частина інваріанта.

Типова помилка — сховати ДІЮ в інваріант: `(loader :requires validate-then-MarkAsLoaded)` —
це не властивість, це порядок кроків. Пиши як дію: `(order → validate, THEN MarkAsLoaded())`.

## 5. Вкладення

Вкладення — це **анкета одного суб'єкта**: зовнішня дужка задає контекст, внутрішні — його
поля. Використовуй, коли в одного суб'єкта 3+ аспекти, які втрачають сенс окремо:

```lisp
(routing :spawn
  (loop            → per config entry, TrySpawn down the list, first match wins)
  (input           → one authored config → one owner)
  (unhandled-kind  → FAIL LOUD)                ;; кайнд без спавн-підсистеми = баг авторингу
  (use-for         → materializing config → entities))
```

Як читати: зовнішній рядок — заголовок («режим routing, варіант spawn»), внутрішні — його
характеристики. Поля всередині НЕ читаються без контексту зовнішньої дужки.

Правила вкладення:
- **Глибина ≤ 2.** Третій рівень означає, що ти описуєш структуру даних, а не правило —
  розбий на два суб'єкти.
- **Вкладати можна тільки залежне.** Якщо внутрішній рядок має сенс сам по собі — це
  окреме правило верхнього рівня, не поле анкети.
- **Паралельні анкети — поруч і з однаковими полями** (як `routing :spawn` та
  `non-routing :evaluator` у PATTERN_POLYMORPHIC_CATALOGUE) — тоді різниця читається як діф.

## 6. Групування і вирівнювання

- Секції всередині одного fence — коментар-розділювач: `;; ── назва секції ─────────`.
- Колонка `→` вирівнюється пробілами: сканування таблиці очима — половина її цінності.
- Один рядок = одне правило. Два правила через кому в одному рядку — не пиши.

## 7. Алгоритм писання (шпаргалка)

1. Скажи правило вголос одним реченням.
2. Знайди суб'єкт (про що воно?) — він іде першим, у kebab-case або як точне ім'я API.
3. Вибери тип за §3: дія / інваріант / розгалуження.
4. Вербалізуй вердикт коротко; альтернативи — через `|`; критичне слово — CAPS.
5. Додай `;; why` одним підрядним. Не влазить в одне підрядне? Це design decision —
  пиши прозовий абзац, а не рядок таблиці.
6. Перечитай уголос за схемою §1. Якщо речення не складається — правило сформульоване криво.

## 8. Що НЕ конвертувати в таблиці

Проза лишається прозою для: **інтенту** (навіщо модуль існує), **rationale** (чому так
спроєктовано), **поведінкових контрактів** (side-effects, live-vs-copy, порядок викликів).
Нюанс там і є корисним навантаженням — таблиця його вб'є. Евристика: якщо для правила
хочеться другого речення — це не правило.

## 9. Тренування — прочитай і звір

```lisp
(grep-family  :session main :grep-budget<4 → ALLOW (counted))
```
*«Grep-подібний пошук у головній сесії дозволений і рахується, поки бюджет менше 4».*

```lisp
(forget-EventTag → the entity LEAKS)   ;; живе вічно, With<Event> матчить його щокадру
```
*«Забув EventTag — сутність тече: живе вічно і матчиться щокадру». Інваріант-наслідок.*

```lisp
(depends :presentation→domain → one-way, onto what it renders)
```
*«Presentation залежить від доменів лише в один бік — тільки від тих, кого рендерить».*

```lisp
(shape :engine-refs|sub-config-lists → WRAP live SO ref)
```
*«Якщо конфіг несе engine-посилання або списки суб-конфігів — компонент обгортає живий SO».*

Живі приклади для читання: `.claude/SEARCH_POLICY.md` §2, `ARCHITECTURE.md`,
будь-який `Patterns/PATTERN_*.md` → Rules.

## 10. Постановка задачі у LISP

Користувач ставить задачу компактним s-expr замість прози, коли **логічний зв'язок легше
показати стрілками, ніж описати словами**. Це НЕ Engineering Task Template у дужках —
у LISP їде тільки суть (`goal`); решту блоків шаблону агент добирає питаннями, як завжди.

Форма — анкета §5 із суб'єктом `task`:

```lisp
(task "DistrictBuild: confirm click → event → orchestrator"
  (goal
    (event        → NEW one-frame event, fired on [confirm] click in DistrictBuildUIView)
    (orchestrator → NEW system in BuildDistrictAction; listens event → creates entity with components)))
```

Як читати:
- **Заголовок** — ланцюжок «що звідки куди тече», не назва тікета.
- **`goal` — по одній внутрішній дужці на механіку** (глибина 2 — стеля, §5). Кожна дужка —
  одна річ, яку можна обговорити/прийняти/відхилити окремо.
- **`NEW`** (CAPS, §1) позначає те, що треба СТВОРИТИ — на відміну від існуючих імен
  (DistrictBuildUIView), які є контекстом.
- Стрілка всередині дужки — потік: `listens event → creates entity` читається як
  «споживає X і внаслідок цього продукує Y».

Контракт для агента:
- Такий s-expr = блок «Задача» шаблону, точніший за прозовий. Гейт шаблону діє як завжди:
  блоки, яких у постановці нема (scope, pattern, рішення, skip, результат), агент
  **питає, не вигадує** — але тепер питання цілиться у конкретну дужку `goal`.
- Точні імена у дужках (типи, view, папки) — якорі: агент трактує їх буквально,
  а не як приблизний опис.
- За бажанням користувач МОЖЕ додати поля-анкети поруч із `goal` (`scope :only`, `pattern`,
  `decided`, `skip`, `result` — повний скелет: CLAUDE.md → Engineering Task Template) — тоді
  відповідне питання знімається. Відсутнє поле ≠ «нема обмежень», відсутнє поле = «спитай».

Як набрати `→` на маку — системної комбінації для цього символа нема, тож:
- **Text Replacement** (найзручніше): System Settings → Keyboard → Text Replacements,
  додай заміну `->` → `→` — далі стрілка друкується сама у будь-якому аппі;
- разово: `Ctrl+Cmd+Space` (Character Viewer) → пошук *rightwards arrow*;
- **або просто пиши ASCII `->`** — у постановці задачі він еквівалентний `→`,
  агент читає обидва однаково.

## 11. Це канонічний LISP? Ні — «за мотивами»

Від Lisp запозичена лише **s-expression-нотація**: дужки, суб'єкт першим елементом,
`;;` коментар, `:keyword`-кваліфікатори (відлуння keyword-аргументів Common Lisp).
Далі — свідомі розбіжності:

- Канонічний Lisp — **мова, що виконується**: перший елемент списку — функція, решта —
  її аргументи, все обчислюється. Наші рядки ніхто не виконує — це нотація для правил.
- `→`, `|`, CAPS-наголос — власні оператори цього репозиторію; у Lisp їх нема.
- Немає семантики обчислення, quoting, макросів — і не треба.

Тобто це **DSL у s-expr-одязі**: від Lisp взято рівно те, що робить запис однозначним і
сканованим (структура дужок), а не мову цілком. Перевіряти запис Lisp-інтерпретатором
безглуздо; критерій правильності — читання вголос за §1.

### Clojure — живий діалект, з якого можна красти

Clojure (Річ Гікі, 2007) — сучасний Lisp на JVM: функційний, незмінні дані за замовчуванням.
Для цього гайду він цікавий не як мова, а як **донор нотації**: його s-expr розширений
літералами, яких у класичному Lisp нема. Кожен — з прикладом «як у Clojure» і «як це
виглядає у постановці задачі».

**`:keyword` — самозначуща мітка.** Ім'я, що означає саме себе: не змінна, не рядок,
просто маркер. У Clojure ними позначають ключі мапи:

```clojure
{:name "Lviv" :tier 2}   ;; ключі мапи — keywords
(:tier city)             ;; «дістань поле :tier з city»
```

У нас це вже є — кваліфікатори `:only`, `:session`, `:must-not` — та сама ідея: мітка,
яку не можна сплутати зі значенням.

**`[a b c]` — вектор.** Упорядкований список: без ком, у квадратних дужках — щоб очима
відрізнявся від круглих (дій):

```clojure
["BuildDistrictAction" "DistrictBuildUIView"]   ;; Clojure: вектор рядків
```

У постановці — перелік файлів/значень одним рядком, без буліт-пойнтів:

```lisp
(scope :only → [BuildDistrictAction/ DistrictBuildUIView])
```

**`{:k v, :k2 v2}` — мапа.** Пари ключ→значення у фігурних дужках; кома = пробіл,
можна не писати:

```clojure
{:name "Lviv" :population 720000 :capital false}
```

У постановці — кілька дрібних полів одним рядком замість розгорнутої анкети:

```lisp
(task "..." 
  (goal ...)
  {:skip AP-spending  :result event-flows-UI→ECS})
```

**`(-> x f g)` — threading macro, «протягни крізь».** Бере `x`, підставляє у `f`,
результат — у `g`. Спосіб записати конвеєр зліва направо замість вкладених дужок,
що читаються зсередини назовні:

```clojure
(-> city (assoc :tier 3) (update :population inc))
;; те саме без ->, навиворіт: (update (assoc city :tier 3) :population inc)
```

Найцікавіший збіг: наш заголовок задачі `"confirm click → event → orchestrator"` —
рівно ця думка, знайдена незалежно. У Clojure це виконуваний оператор
`(-> click event orchestrator)`; у нас — читабельний ланцюжок потоку.

Правило для експериментів з формою: дозволено все, що агент прочитає однозначно вголос;
новий літерал (вектор, мапа, будь-що) — просто зафіксуй тут у гайді, як §2 фіксує
оператори. Визначена один раз нотація перестає бути здогадкою агента і стає контрактом.
